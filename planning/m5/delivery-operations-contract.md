## Explicit outreach and review notices

The owner of a private follow-up selects **Send approved message** separately from approval or manual download. The shared confirmation identifies the subject, recipient and version, explains that replies go to the owner's verified account, and warns that a reserved send cannot be recalled. Cancel has initial focus; Escape restores the trigger. Approval alone still sends nothing. Existing manual download remains available.

`POST /automation/drafts/{draft}/send` accepts the displayed version only. The server reuses M5-07's approval, active-lead, current membership/verification/entitlement, consent, schedule/run/rule and exact-version locks. It records one durable `follow_up.outreach` intent per draft/version and an audit event atomically. Repeated requests return the same intent, including after an uncertain outcome; they never replay it. Saving and explicitly approving a fresh version is required for a new outreach attempt. Workspace/platform administrators cannot inspect or send another person's drafts through tenant endpoints.

The worker rechecks the current basis under the same locks before reserving the send. The configured application sender delivers a plain-text message containing exactly the reviewed subject/body; Reply-To is the owner's current verified account. No private CRM interpolation, attachments, mailbox access or AI is involved. Scalar routing IDs alone enter Redis/failed jobs. Recipient/content stay in the private draft table; no second plaintext queue payload is introduced. Stable Message-ID is the outbox ID and does not claim SMTP deduplication.

**Follow-up review emails to my account** is a new, default-off preference. A versioned append-only consent event records the choice. New manual/scheduled drafts can create one generic review notice addressed only to the owner's current verified account; neither the draft recipient nor its subject/body/CRM details appear in the notice. Existing drafts are not backfilled. Preference saves cancel pending older review intents atomically; enabling the preference later does not revive them. Edits/approval/discard/reply cancel pending notices for obsolete draft versions. Restored access never restores old approvals.

The inbox hides Send after an intent exists for that version and shows the request in private email history. History distinguishes pending, reserved, local capture, transport acceptance, cancellation and uncertainty. None establishes mailbox receipt. A send reserved before a reply/access change may finish; an already downloaded file cannot be recalled. Tests cover both real PostgreSQL lock orders for reply versus outreach reservation.

## Dispatch, backoff and budgets

PostgreSQL reconstructs pending work after queue loss. Dispatch selects up to 100 eligible records, taking one turn per workspace before its next turn and prioritizing workspaces that reserved mail least recently. It acquires workspace locks in organization order and returns the original fair queue order. A 60-second dispatch lease prevents concurrent/repeated publication from flooding Redis; a crash before publication leaves the intent eligible after lease expiry.

Queue publication failure and unsupported transports retain pending intent with a sanitized failure code and bounded exponential backoff: 60 seconds through one hour. Other workspace turns continue after a queue failure. No exception text, credentials, capability links or message bodies are stored as feedback. Only SMTP and local/testing array transports are supported; log/failover transports cannot expose messages.

`NOTIFICATION_WORKSPACE_PER_MINUTE` and `NOTIFICATION_GLOBAL_PER_MINUTE` are nonnegative fixed-minute reservation limits. **Implementation default:** zero is unconfigured and preserves existing development delivery; it is not an approved production allowance. A content-free PostgreSQL counter function serializes competing workspaces and commits consumption with the send reservation. Redis restarts cannot reset the budget. A budget denial or invalid numeric configuration defers pending work for 60 seconds without starting an external attempt; invalid settings cannot silently turn limits off. Eligibility and budget windows use database time. A transport exception or crashed reservation remains uncertain and never returns to pending.

**Assumption / Open:** actual provider limits, any rolling-window/daily/spend caps and production values still require acceptance before live delivery. These fixed-minute controls cover business outbox reservations; existing account verification/reset paths keep their own throttles and are not counted here. Production budget acceptance must account for that traffic too. No provider-specific cap or measured throughput is claimed. M5-09 provider receipt and M5-10 broader outage/restart acceptance remain separate.

## Operator permissions and resolution

The existing offline `platform:grant` procedure accepts separate `notifications.read` and `notifications.reconcile` permissions, with accountable operator/reason, existing verified identity, versioned grants and MFA/session invalidation. No real grant/account is provisioned by this implementation. A tenant owner role grants no platform authority; the existing platform-owner capability includes the new scoped operations.

`GET /admin/notifications` requires a current grant and 15-minute password/authenticator proof. It returns bounded, paginated metadata filtered by workspace ID/state: routing ID, kind, state, timestamps, availability, deferral count/code and recorded resolution. Recipients, message bodies, capability ciphertext/URLs, raw exception text and queue payloads are excluded. New operational tables have forced RLS and no direct runtime mutation policies. Ordinary tenant read policies remain actor/workspace scoped.

`POST /admin/notifications/{notification}/resolve` additionally requires `notifications.reconcile`, an exact unresolved version and a nonblank reason. **Implementation default:** record one immutable audited resolution per uncertain record: provider transport acceptance, provider confirmation of no send, or closure with the outcome still unknown. Stale/duplicate requests fail with 409. The original uncertain transport state remains intact, and the resolution/audit commit or roll back together. This never requeues the record, replaces a capability or grants outreach approval. Provider acceptance still does not prove recipient receipt. Confirmation uses the shared dialog; filters and safe server errors survive navigation.

To send again, the authorized tenant actor creates an appropriate replacement invitation or saves/reviews/approves a fresh follow-up version and explicitly requests sending. The operator cannot read private content or make that decision for them. The directory links to diagnostics only when the read permission permits it; an operator with notifications-only access lands directly in diagnostics after MFA.

## Migration and handoff boundary

The two additive migrations preserve existing business records and add routing/provenance, deferral fields, operational counters, immutable resolutions, narrow functions/policies and opt-in preference storage. Fresh install and rollback/reapply with retained old-format records are tested only in synthetic databases. Rollback explicitly refuses to remove follow-up delivery or operator-resolution history; no automatic destructive downgrade is supplied. A reviewed backup/recovery plan is required for such a downgrade. This slice does not claim a restore drill.

Only isolated synthetic databases receive these migrations in this session. For a later rollout, pause dispatch/workers, apply migrations through the migration role, replace app/worker/scheduler code and built assets together, then resume after checks. Old workers cannot safely consume the new notification kinds; rolling-version compatibility is not claimed.
