## Priority and scope

Implement this package next, starting with ADM-01. Then resume UI-07, broader UI-05 reference/deviation acceptance and M5-02–M5-10. Do not advance to the next milestone or declare launch readiness before the required administration gates pass. Existing UI-06 changes are checkpointed in `2aaeca1`; all unfinished tasks remain preserved. This planning update implements no administrator account, dashboard, permission, MFA or cleanup behavior.

Required outcomes are a platform-owner/super-admin access path, account/workspace management, plan/entitlement administration, notification/job diagnostics, audit review and controlled support access. The initial real platform-owner account must survive test-data cleanup and be provisioned separately from synthetic fixtures. Platform administration remains distinct from tenant Owner/Admin membership.

**Proposal / implementation defaults:** use the existing Laravel identity/session system with an explicit platform grant and a separate `/admin` area. Start with one accountable platform-owner capability and explicit scoped operator capabilities as needed; do not infer global access from a workspace role or an email address. Detailed schema, endpoint names and operator delegation matrix must be recorded during ADM-01 before implementation. These defaults are not existing application behavior.

## Permission and data boundaries

Platform operators need narrowly scoped cross-workspace metadata and administration capabilities, not ordinary membership in every tenant. Design and test those paths explicitly with PostgreSQL RLS; tenant web requests, workers and normal runtime queries retain existing isolation. Do not introduce a general-purpose runtime superuser or migration-role connection. Required schema/permission changes need migration/rollback and denied-operation coverage against real PostgreSQL.

Audit successful and rejected privileged actions without passwords, MFA secrets, reset/invitation URLs, document contents or private notes. Version checks and transactional writes must keep access state, entitlement changes and audit consistent. The initial account/recovery identity and exact production operator roster are **Assumption / Open**; do not create a guessed account or put credentials in planning files. Actual hosting, privacy/retention policy, commercial packaging and uncertain-send decisions remain under their existing task IDs.

## Verification and completion boundary

Required tests cover privilege escalation, direct-route/JSON denial, MFA and recovery bypass, grant revocation, suspension across sessions/jobs/capabilities, last-owner protection, entitlement concurrency, support grant expiry, audit integrity and cross-tenant leakage. Use existing PostgreSQL, PHPUnit, Vitest, Playwright and Pint tooling. Validate actual runtime database roles; SQLite and mocked RLS do not establish isolation.

All visible administration work follows the [mandatory UI standards](../AGENTS.md#mandatory-ui-standards-for-every-milestone): shared shell/sections/fields/actions/confirmation dialog, pinned Prettier, type checking/build, desktop/mobile keyboard and browser checks, inspected screenshots and recorded evidence. Errors and recovery guidance must remain usable after transient toasts close.

Record implemented versus unverified behavior, exact tested revision/environment, migrations, commands/results and outstanding policies in this contract and the [register](remaining-tasks.md). Close ADM tasks only with evidence. This package does not waive unfinished M5 workflows, M1-04 owner MFA, M3-02 privacy, M4-01 commercial decisions, M5-08 delivery operations or M6 readiness/UAT. Production rollout, live-data cleanup and external messages retain separate execution authorization.
