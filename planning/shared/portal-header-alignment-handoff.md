# Portal header alignment — Claude correction handoff

Date: 2026-11-24. Inspected baseline: `9270cdd`, following navigation/Home `2a161c2`. Status: implemented on 2026-11-25 on branch `feat/portal-header-alignment` (stacked on `feat/appearance-preference`), with approved follow-ups for the navigation scrollbar, Collapse visibility and sidebar width/gutter; see [implementation evidence](portal-header-alignment-evidence.md). Not merged or deployed.

## Requested correction

**Confirmed:** the user reports the header does not match v2: search should sit toward the left with a slightly transparent background, and the avatar should have text beside it. Use the selected workspace name for that text. Apply the shared treatment across Brand, Partner and Professional without changing the sidebar/Home or personal appearance contracts.

**Mockup:** [Main](../../mockup/v2/Main.dc.html) and [Partner detail](../../mockup/v2/Partner.dc.html) arrange the desktop header as branding → flexible search → right-side account/actions. Search uses a white background at 14% opacity, approximately 44px height, 10px radius and an icon; its input background is transparent. The right-hand outlined button contains a workspace label followed by the avatar. Sample names and initials are not product data.

## Findings in current source

- [PortalShell](../../src/resources/js/layouts/PortalShell.vue) puts its `actions` slot inside `.wd-portal-actions`, which has `margin-left: auto` in [portal-shell.css](../../src/resources/css/portal-shell.css). Consequently search supplied through that slot sits with the right-side account controls.
- [PartnerChrome](../../src/resources/js/features/portals/PartnerChrome.vue) supplies search through `#actions`; the input has `bg-white`, `text-ink` and `placeholder:text-muted`, so it is opaque rather than the mockup's translucent field.
- [AccountMenu](../../src/resources/js/components/AccountMenu.vue) renders an avatar-only trigger. The workspace name is instead beside the logo in the shell and hidden below 600px. [usePortalContext](../../src/resources/js/composables/usePortalContext.ts) already exposes the authorized selected workspace name.
- The existing header search is Partner lead search, not global search. Professional currently delegates to its own shell before the Partner search markup. Brand and Professional do not acquire search functionality merely from repositioning the shell slot.

## Implementation instructions

1. Add a dedicated optional header `search` slot between the masthead and right-side actions in `PortalShell`. Move the existing Partner search into that slot, including fixture support. Keep page actions such as Invite partners in the actions group; do not reposition unrelated page tools or add a second search input.
2. Let desktop search grow from the left after branding into available middle space, with a sensible maximum around the mockup's 720px. Use shrinkable flex/grid children and avoid a fixed spacer or absolute-positioned field. Keep account/actions aligned right and readable with long workspace names. Search must not move into the sidebar.
3. Use shared search styles with a translucent white surface on Burgundy/Purple headers, transparent input, inherited light text/icon and a readable light placeholder. Approximately `rgb(255 255 255 / 14%)` is the reference starting point; verify contrast. Preserve visible focus and a labeled search control. For Brand's retained white header, use an appropriate token-based tinted surface and dark text; do not blindly apply white-on-white styling or change its header tone.
4. Extend the existing `AccountMenu` trigger with an optional workspace label supplied by `PortalShell` from its existing computed `workspaceName`. Put that label immediately before the existing avatar in one outlined button, following v2. The initials still represent the signed-in account. Preserve the menu identity, appearance/security/privacy/workspace-switch links, authorization, logout and keyboard interactions. Outside portal shells, preserve existing avatar-only behavior unless a real workspace label is intentionally supplied. Do not create a second menu or pretend the button directly switches workspaces; it opens the existing account menu containing the switch action.
5. Avoid redundant full workspace names at both ends of the header: keep logo/experience identity left and put the selected workspace name beside the avatar right. Retain the drawer workspace description. Use real selected workspace data and update reactively after switching; do not fall back to mockup names or a stale browser value. With no selected workspace, omit the workspace label gracefully.
6. Keep the workspace label visible with the avatar on mobile as space allows, truncating long names accessibly. At 320px allow a deliberate additional row rather than dropping the context label or creating horizontal overflow. Search can occupy a full-width row below the compact masthead/account row. Update selectors currently tied to `.wd-portal-actions:has(.wd-portal-search)` so the new slot works. Keep drawer focus/escape behavior and touch targets intact.
7. Keep Partner search's label, `q` parameter, Enter submission, current value and My leads destination intact. Do not add unsupported cross-resource placeholders such as “Search partners, deals, contacts”. Brand/Professional search remains absent where no functional scope exists; the shared slot supports future authorized search, but this correction does not authorize a new search backend or disabled decorative input.

**Assumption / Open:** if the user wants working header search on Brand and Professional as well, its search scope/destination needs a separate contract. Complete the confirmed positioning/style/account-label correction without blocking on that potential expansion.
